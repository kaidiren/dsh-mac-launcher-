# 背景与验证记录

本文记录**为什么**这样设计，以及重构前后的实测数据。
（使用、配置、排错请看 [README](../README.md)。）

## 一、为什么要重写

原 `dsh-launcher` 不是"一个应用"，而是**五个协作体 + 一堆文件状态**：

```
Dock 图标 (DSH Web.app —— 只是 3 行 shell 薄壳)
      ▼
launch-dsh-web.sh (545 行 bash，真正的逻辑)
      ├─ 原子 mkdir 锁串行化整段流程
      ├─ lsof 探端口 → 决定是否拉起 dsh web
      ├─ tail/grep 日志 → 抓带 token 的认证 URL
      ├─ curl 探 303/401 → 校验 token 是否还有效
      ├─ osascript → 枚举 Chrome 窗口（检测/聚焦/撑满/关闭）
      ├─ screen-bounds (Swift 工具) → 取屏幕可用区域
      ├─ 直接 exec Chrome 二进制 --app=<url> → 开出应用窗口
      └─ 拉起 dsh-tray (Swift，独立进程)
                └─ 托盘不能自己发 AppleScript（TCC 按发起进程判定）
                   → 只能写 .dsh-stop-request-<port> 标志文件
                   → 再 open -a "DSH Web.app" 让 app 去执行
```

状态分散在 7 处：`dsh-web.pid`、`dsh-web.url`、`dsh-web.log`、`dsh-tray.pid`、
`.dsh-start.lock/`、`.dsh-stop-request-*`、`.dsh-restart-request-*`，外加 `chrome.log`、`tray.log`。

**关键判断**：这些复杂度几乎全部来自"用 Chrome 当窗口"这一个选择，而不是需求本身。
需求只有三件事：起服务、开窗口、能停掉。

## 二、问题清单（按严重度）

### A. Chrome 依赖链：一次点击牵动 5 个环节、1 项系统权限

1. **首次点击弹授权框**："『DSH Web』想要控制『Google Chrome』"。用户按 README 得知道要点允许，
   否则**每个窗口都重复开**。
2. **TCC 按"发起进程"判定**，托盘不能自己干活 → 标志文件 + `open -a` 绕行 →
   又需要端口隔离 + 90 秒保质期。旧 README 的坑 #7、#8 全由这一条衍生。
3. **失败静默**：权限被拒时 osascript 返回空字符串且 rc=0，症状是"重复开窗"，日志里也不显眼。
4. **`--start-maximized` 在 Chrome 已运行时被丢弃** → 只能自取屏幕尺寸再 AppleScript
   `set bounds`，还要循环重试 24 次（最长 12 秒）。
5. **窗口检测最长阻塞 10 秒**，且要给用户点授权框留时间——一次点击的延迟不可控。
6. **单一故障点**：卸载/移动 Chrome、或 Chrome 更新改变 AppleScript 字典，启动器即失效。
7. **耦合日常浏览器**：GUI 是用户日常 Chrome 的一个窗口，和标签页争资源；Chrome 崩溃窗口即消失。

### B. 架构问题

8. **没有单一状态源**：pid、url、锁、标志、日志各写各的，靠文件名和保质期互相猜。
9. **App 是薄壳**：`DSH Web.app` 只有 3 行 shell，无进度显示、无法给出错误 UI。
10. **每个动作都要重启一次 app 再读标志**：点"退出"链路长且难调试。

### C. 体验问题

11. **看不出服务状态**：窗口关了服务还在，但只有菜单栏图标 tooltip 能看出。
12. **重启会丢认证**：服务重启 → token 变更 → 需要走"日志里找回 URL"。
13. **运行期文件写在源码目录**（`dsh-web.log` / `dsh-web.url` 落在 `dsh-launcher/`）。

## 三、可行性验证（重构前实测）

动手之前先用一个真实的 Swift + WKWebView 原型跑通全链路：

| 验证项 | 结果 | 证据 |
|---|---|---|
| token URL 自动完成认证 | ✅ | 加载 `?token=` → 服务端 303 → WebView 内落到 `/`，`dsh-auth-*` cookie（HttpOnly, SameSite=Strict, 30 天）写入 |
| GUI 完整渲染 | ✅ | 标题 `DeepSeek Harness`，渲染出真实会话列表、工作区、余额，`__DSH_BOOT__` 存在 |
| 无 token 时的行为（对照） | ✅ | HTTP 401 + `dsh web authentication required...` —— 认证墙可被程序检测 |
| **跨进程 cookie 持久化** | ✅ | 第 1 次用 token URL，第 2 次仅用根地址**免认证直接进 GUI** |
| WebSocket 长连接 | ✅ | 多条到 `127.0.0.1:3080` 的 ESTABLISHED（端点 `/api/remote.mux`，同源、依赖 cookie） |
| 剪贴板 API 风险 | ✅ 低 | 前端只在 shell 包里用 `navigator.clipboard.writeText`，且有 `execCommand` 降级 |
| 文件上传 | ✅ | `<input type=file>` → WKWebView 原生弹 NSOpenPanel |
| 是否需要 Electron 桥 | ✅ 不需要 | 前端无任何 Electron/桌面环境检测分支 |
| 窗口占满屏幕 | ✅ | 原生 `NSScreen.visibleFrame`，替代 `screen-bounds` + AppleScript |

前端技术栈调研（覆盖全部 55 个客户端插件）要点：

- **唯一 WebSocket**：`/api/remote.mux`，无子协议、URL 无 token，认证靠同源 cookie；
  带指数退避自动重连（500ms 起、×2、上限 10s）。
- **必须加载真实 http origin**：前端在 `location.origin === 'null'` 时会静默退化到
  `http://dsh.internal`（不存在的域名）→ 所有 RPC/WS 全挂且没有明确报错。
  所以不能用 `loadHTMLString` / `loadFileURL` / 自定义 scheme。
- **索引页依赖服务端内联注入**（`__DSH_BOOT__`、`__DSH_CONNECTION_RECOVERY__`、`<base href="/">`），
  直接读 `dist/index.html` 会抛 `window.__DSH_BOOT__ is missing`。
- **认证密钥持久化**：签名密钥写进 credentials 记录；cookie 只绑 authority + 过期时间，
  **不绑进程级 launch token** → 服务重启后仍保持登录。但 `?token=` 那个 launch token
  是每进程随机的，**跨进程会失效**（这一条决定了"缓存 token ≠ 长期可用"）。
- **无 CSP / COOP / COEP**，不需要跨源隔离。
- **现代 JS 门槛**：`AbortSignal.any`、`Promise.withResolvers` 用在连接代际的关键路径上且无 polyfill，
  PDF 预览还用到 `Promise.try` → 本启动器在 `documentStart` 注入这三个的兼容实现。
- 未使用：`indexedDB`、Service Worker、SharedWorker、File System Access API、`crypto.subtle`、
  `Notification`、Chrome 专有 API。

### 实现中踩到并修掉的坑

1. **`MainActor.assumeIsolated` 在后台队列上 = 直接 trap**。
   等待端口就绪的循环跑在后台队列，却去断言"我在主 actor 上"→ `dispatch_assert_queue_fail` 崩溃。
   改为 `AtomicFlag`（NSLock 保护的布尔）跨线程传递"子进程是否已退出"。
2. **非阻塞 `connect` 的 `EINPROGRESS` 不等于端口可达**。
   最初把 `EINPROGRESS` / `EALREADY` 当作"有服务"，导致空端口也报"服务已在运行"。
   必须 `select` + `getsockopt(SO_ERROR)` 取回真正的握手结果。
3. **在 `applicationWillTerminate` 里同步等待 `@MainActor` 的 `stop()` = 死锁**。
   表现极具迷惑性：日志打印了"应用退出：停服务"，服务却始终活着。
   改为异步退出流程：先 `await service.stop()`（带 8 秒硬上限），完成后再 `NSApp.terminate`。
4. **`dsh web` 收到 SIGTERM 后可能因活跃连接迟迟不退** → 宽限 3 秒后升级 SIGKILL。
5. **`__DSH_BOOT_READY__` 在客户端插件加载完成前就已置位**，
   用它判断"页面就绪"会过早撤掉启动遮罩、露出 `Loading plugins…`。
   改为"内容长度 > 200 且连续两次不再变化"。
6. **正则插值写错**：`"...:\\(port)/..."` 里的 `\\(` 是字面量，导致"从日志恢复认证 URL"
   永远匹配不到（`firstAuthURL` 里写对了，`lastAuthURL` 里写错了）。
7. **`start()` 与「重启服务」会并发**（自省测试暴露）。冷启动流程走到"加载界面"那一步时，
   服务可能正被菜单栏动作换掉：`start()` 只看到"端口有监听"就继续加载，撞上
   "端口关了又开"的窗口期，白跑一串连接失败重试（实测 5 次 `-1004`）。三层修复：
   `ServiceController.startIfNeeded()` 在重启期间等待；`WebWindow` 用 `restarting` 标志
   拦住重启期间的加载；重启流程等「端口就绪 + 新 token 到手」后自行加载一次
   （拆出 `performLoad()` 供它绕过拦截）。修完：加载 1 次、401 0 次、连接失败 0 次。
8. **`--print-decision` 曾被单实例守卫挡掉**。自检是只读的，不该被"已有实例在运行"影响、
   也不该起服务或开窗；现已提到守卫之前，并顺带打印更多决策项。
9. **菜单栏图标发糊：用错了分辨率**。`Resources/icons/` 里有两份同名图标——
   `tray-iconTemplate.png`（16×16）与 `tray-iconTemplate@2x.png`（32×32）。
   我起初加载了 1x 那份、又把逻辑尺寸设成 18pt，Retina 上等于把小图拉大两倍多，于是一团糊。
   原版 `dsh-tray` 用的是 **@2x** 那份（`img.size = 18×18` + `isTemplate = true`）。
   现已照原样改回，并保证两份图标与 dsh-launcher 里的逐字节一致。
10. **不能为"别人的服务"自动重启**。最初逻辑在拿不到 token 时会重启服务——
   若那个服务是用户在终端里手动跑的，就会打断其会话；`SO_REUSEPORT` 下还可能
   出现两个进程同时绑定同一端口。现在：别人的服务只尝试从日志恢复认证地址，绝不重启。

## 五、设计取舍

- **为什么保留"关窗不退出"**：与原版语义一致（窗口只是服务的一个客户端），
  且服务冷启动约 10 秒，每次关窗都停服务会让二次打开很慢。
- **为什么菜单栏图标跟随应用生命周期**：旧版常驻独立进程是为了"窗口关了还能操作服务"；
  本版把窗口与服务收进同一进程后，图标跟着应用即可，代价是退掉应用图标就没了
  （服务仍在跑，重开应用即可）。换来的是零 IPC、零标志文件。
- **为什么认证优先走 cookie 而不是 token URL**：本地回环只有一次 GET，省掉 303 往返，
  也避免把 token 写进 URL 与历史记录。token 只在 cookie 失效时用一次。
- **为什么不用 Electron**：DSH 的 `desktop` profile 由另一个 Electron 应用专用，
  但引入 Electron 等于把 1.4 GB 的 Chrome 换成 200 MB+ 的 Chromium —— 与"更轻"的目标相反。
  WebKit 随系统提供，零额外体积。
